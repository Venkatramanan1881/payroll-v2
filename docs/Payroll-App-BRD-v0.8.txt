======================================================================
1. PURPOSE
======================================================================

This document defines a payroll application sold to many organisations in different sectors. Check-in and check-out punches are the only raw facts. Everything else is a layer of rules each organisation adds on top to decide how it pays its people.

The application is not one fixed product. It has a common part that every client gets, and separate modules that the vendor switches on or off for each organisation. Payroll calculation is usually specific to each client, so the software is shaped to the client's requirement on top of a standard base.

The application is delivered in three releases: version 1 for core workforce management, version 2 for loans, advances, payroll and groups, and version 3 for extended workforce capabilities (section 21).


======================================================================
2. OBJECTIVES
======================================================================

O1. One platform serves every sector and worker type. Attendance, leave and the other common parts are handled through settings; payroll calculation is tailored for each client by the vendor.
O2. The vendor decides which modules each organisation gets. The organisation's HR decides how each rule inside those modules behaves.
O3. Same punches plus same rules always gives the same pay, and every figure can be explained.
O4. Nothing adds or cuts pay unless a configured rule or an approval says so.
O5. A standard payroll base is shared by all clients, and client-specific calculation rules are added on top without affecting any other client.

Proposed success measures (to confirm):
- A new organisation is live on the common modules from a template with no code change; client-specific payroll rules are added without changing the common code.
- At least 95% of employee-days are finalised with no manual action.
- Every amount on a payslip can be traced to punches, rules and approvals.


======================================================================
3. TARGET CLIENTS AND WORKFORCE
======================================================================

Sectors: manufacturing, supermarkets, restaurants, bakeries and cafes, service industries.
Workforce: blue collar and white collar; unskilled, semi-skilled and skilled; permanent, probation, casual and contract workers.
Scale: hundreds of client organisations; up to about 2,000 employees per organisation across multiple branches.
Punch methods: biometric device, face (device or selfie in the app), app check-in and check-out, web check-in and check-out. App and web punches capture location and can be geo-fenced.
Platforms: web admin panel for all clients; Android and iOS employee app where the client's plan includes it. Workers without a smartphone use the device only.
Languages: English, Tamil, then Hindi. Each user can change language.

======================================================================

- Organisation Admin: manages users, roles and branches. Approves period unlock.
- HR Manager: owns settings, policy sets, payroll groups, waivers and HR-level approvals. Can be limited to chosen branches. Responsible for device enrolment, opening balances and manual attendance when a device fails.
- Payroll Officer: locks periods, runs payroll, releases payslips, records payments.

======================================================================
6. DEFINITIONS
======================================================================

Punch: one recorded check-in or check-out event.
Session: a matched in and out pair.
Attendance date: the working day a punch belongs to.
Grace: minutes tolerated after shift start or before shift end.
Geo-fence: a circle around a branch (centre point and radius) inside which an app or web punch is accepted.
Late mark / early mark: a recorded instance of late arrival or early check-out.
Permission: a short approved absence inside the working day, limited per month.
On-duty: approved official work away from the workplace, counted as worked.
Master branch: the branch an employee belongs to.
Allowed branches: other branches where the employee may punch.
Absconding: continuous uninformed absence beyond a set number of days.
Client-specific rule: a pay calculation rule built by the vendor for one organisation.
Regularisation: a request to correct attendance, approved by a manager or HR.
Informed leave: leave with a request approved before the day, or approved afterwards.
Uninformed absence: an absent day with no approved leave request.
Sandwich policy: weekly offs or holidays that fall between leave or absent days are counted as leave or absence.
LOP: loss of pay.
Deduction days: LOP days plus any extra days cut by a rule (for example the second day of a double cut).
Comp-off: a paid day off earned by working on a holiday or weekly off.
Payroll group: a set of employees paid by the same rules, frequency and payment method.
Monthly salary: the fixed monthly pay of an employee, before deductions.
Daily allowance: a fixed amount earned for each day worked, paid in addition to the monthly salary and not part of CTC.
Day divisor: the number of days used to turn a monthly salary into a per-day rate.
Piece rate (task-based pay): pay per unit of output or completed task. Not yet scheduled.
Advance: money given early and recovered in full from the next pay.
Loan: money recovered in instalments over several pay periods.
Policy set: a named bundle of settings assigned to a group of employees.
Period lock: the point after which a pay period's attendance can no longer change.


======================================================================
7. CONFIGURATION PRINCIPLES
======================================================================

G1. Two levels of control. The vendor switches modules. HR switches rule groups inside them and sets every option.
G2. Master switch. Every rule group has an on/off switch. When off, the rule is not evaluated and has no effect on status or pay.
G3. Policy sets. Attendance settings are grouped into named policy sets, assignable at organisation, branch, department, category, shift or employee level. The most specific assignment wins.
G4. Payroll groups. Pay settings are grouped into payroll groups that HR creates freely.
G5. Effective dates. A version in use is never edited. A change creates a new version with a start date.
G6. Defaults and templates. Every setting has a default. Starter templates are provided per sector: Factory, Supermarket, Restaurant and bakery, Office and services.
G7. Exemptions. Any rule group can exempt chosen categories, departments, employee types, employees or dates.
G8. Preview. For any setting that affects pay, HR sees a plain-language summary and can test it on last period's data before it goes live.
G9. Settings history. Every change records who, when, old value, new value and reason.
G10. Client-specific rules. Where settings are not enough for a client's pay calculation, the vendor adds a rule for that organisation only (10.3.7).

All defaults in this document are proposals for review.


======================================================================
8. HOW PUNCHES BECOME PAY
======================================================================

Layer 1. Punches: in and out events from devices and the app.
Layer 2. Schedule: shift, roster, weekly offs and holidays say what was expected.
Layer 3. Attendance rules: breaks, late, early, missed punches and regularisation give a result for each day.
Layer 4. Overlays: leave, permission, on-duty and comp-off change or explain the day.
Layer 5. Period totals: payable days, deduction days, late and early minutes, overtime hours.
Layer 6. Pay rules: the Payroll module turns totals into money (or the totals are exported if Payroll is off).
Layer 7. Recoveries and payment: advances and loans are recovered, and net pay is paid by bank, cash or both.

Each layer only reads the layers below it. A correction in any layer recalculates the layers above it while the period is open.

9.6 ATTENDANCE RULES (C06)

Daily process for each employee and date:
1. Resolve the policy set in force on that date.
2. Assign punches to the attendance date using the shift window.
3. Clean: drop repeat punches, merge very short gaps.
4. Read punches into sessions using the configured mode.
5. Validate. Apply the missed-punch rule or flag the day.
6. Calculate gross hours, breaks, net hours, late minutes, early minutes.
7. Apply overlays: leave, holiday, weekly off, on-duty, permission.
8. Set the day status. Send exceptions to regularisation and recalculate on approval.

Settings: punch reading (PR)
PR-01 Reading mode: first-in/last-out / paired / direction-tagged. Default paired.
PR-02 Repeat-punch window: punches closer than this are one punch. Default 60 seconds.
PR-03 Which repeat punch is kept: first / last. Default first.
PR-04 Minimum gap: an out-then-in gap shorter than this is continuous work. Default 5 minutes.
PR-05 Maximum session length before it is treated as a missed punch. Default 16 hours.
PR-06 Maximum punches per day before the day is flagged. Default 12.

Settings: breaks (BK)

BK-02 Break is paid / unpaid. Default unpaid.
BK-03 Break duration. Default 60 minutes.
BK-04 Break window start and end (window type).
BK-05 Cap on total break minutes per day, and on number of breaks per day.
BK-06 Excess break time: deduct from hours / count as early-check-out minutes / use permission balance / flag only. Default deduct from hours.
BK-07 Break taken outside the window: deduct / flag / both. Default flag.
BK-08 Auto-deduct when no break is punched: on / off, X minutes after Y hours worked. Default off.
BK-09 Several named breaks (lunch, tea), each with its own rule: on / off. Default off.

Settings: day status (DS)

DS-02 Minimum net hours for a full day (hours-based and hybrid). Default: required hours for hours-based; 75% of required hours for hybrid.
DS-03 Minimum net hours for a half day. Default 50% of required hours.
DS-04 Shortfall tolerance: a shortfall smaller than this is ignored. Default 15 minutes.
DS-05 Shortfall below the full-day minimum (hours-based): half day / deduct actual minutes / make up within the week. Default half day.
DS-06 Quarter-day statuses: on / off. Default off.
DS-07 Below the half-day minimum: absent / pay in proportion to hours. Default absent.
DS-08 Sandwich rule: set in Leave (LM-16 to LM-20).
DS-09 Present by default for chosen employees (no punches needed): on / off. Default off.
DS-10 Absent with no leave applied: loss of pay / auto-debit leave in a chosen order / hold as pending for N days. Default pending for 3 days, then loss of pay.

RD-03 Direction: nearest / down / up. Default nearest.
RD-04 Applied to: net hours / overtime / both. Default both.

10.3 PAYROLL (M03) - VERSION 2

10.3.1 Standard base

Every client starts from the same base: employees are placed in payroll groups; each group has a pay frequency and pay rules; each pay run takes the locked period totals and produces earnings, deductions, net pay and a payment split. Client-specific needs are met first by settings and components, and beyond that by client-specific rules built by the vendor (10.3.7).

Pay run steps
1. Lock attendance for the group's period.
2. Pull inputs: payable days or hours, deduction days, late and early minutes, approved overtime, extra shifts, comp-off payouts, approved reimbursements, advance and loan recoveries, adjustments from earlier periods.
3. Calculate earnings, deductions and net pay.
4. Review: exceptions such as net pay below zero, missing bank details, employees on hold.
5. Approve the run.
6. Release payslips and produce the bank list and the cash list.
7. Record payments and close the run.
A correction after closing goes into the next run as an adjustment.

Requirements
PY-R1 Wage types: monthly salary, daily wage, hourly wage. Piece rate follows in a later release.
PY-R2 Pay frequencies: daily, weekly, bi-weekly, monthly.
PY-R3 Organisation-defined earning and deduction components, each fixed, a percentage of another component, or entered per run.
PY-R4 A pay master per employee: payroll group, wage type, salary or rate, components, daily allowance amount where enabled, bank and cash split.
PY-R5 Salary revisions with an effective date, and arrears where the date is in the past.
PY-R6 One payslip per employee per run showing attendance summary, earnings, deductions with reasons, net pay, and the bank and cash portions.
PY-R7 Employees download payslips from web and app in their language.
PY-R8 A bank list for transfer and a cash list for payout, with paid and unpaid status.
PY-R9 Hold and release an employee's pay for a run, with a reason.
PY-R10 Final settlement on exit: pay due, comp-off payout, leave encashment where enabled, recovery of advances and loans, notice shortfall.
PY-R11 Net pay never goes below zero. Deductions are applied in a set order; unrecovered advances and loans carry forward.

How pay is worked out
- Per-day rate = monthly salary divided by the day divisor (PY-05).
- Per-minute rate = per-day rate divided by shift hours, divided by 60.
- Monthly salary: salary minus deduction days times the per-day rate.
- Daily wage: rate times payable days. Hourly wage: rate times payable hours.
- Net pay = earnings minus deductions; then split into bank and cash.

PY-02 Earning components: name, type (fixed / percentage / per run), part of CTC or not, affected by deduction days or not.
PY-03 Deduction components: name, type, recovery order.

PY-07 Pay day per frequency (for example the 7th for monthly, Saturday for weekly).

SP-10 Days that count as present for SP-09: paid leave, holidays, on-duty. Each yes / no. Default all yes. A half day counts as half.
SP-11 Weekly off not earned: unpaid (one deduction day for a monthly salary; no wage for a daily wage). Fixed.
An extra shift paid under SP-03 is not also paid as overtime (BR-04).

10.3.7 Client-specific payroll rules

Payroll calculation usually differs from client to client. The standard base covers the common cases; anything beyond it is built by the vendor for that organisation as a client-specific rule.

Requirements
CR-R1 The vendor can add a rule for one organisation at defined points of the pay run: a custom input, a custom earning, a custom deduction, a change to how a standard component is worked out, a custom payslip layout, a custom report.
CR-R2 A client-specific rule affects only that organisation, and only the payroll groups it is assigned to. No other client is affected.
CR-R3 Each rule has a name, a plain-language description, a version and an effective date. It is listed in the vendor console, and in the organisation's settings as read-only.
CR-R4 Before activation, the rule is run against the organisation's last closed period and the differences are shown for the organisation's sign-off.
CR-R5 Client-specific rules obey the fixed business rules in section 12: the explanation is stored, net pay is never negative, closed runs never change.
CR-R6 A rule that proves useful to several clients can be promoted into the standard base as a normal setting.
CR-R7 Client-specific fields can be added to the employee and pay masters for use by these rules.

Settings (CR)
CR-01 Client-specific rules active for the organisation: managed by the vendor only.
CR-02 Assignment: whole organisation / chosen payroll groups.
CR-03 Organisation sign-off required before a rule goes live: on / off. Default on.

10.3.8 Accounting export

Requirements
AE-R1 After a pay run closes, produce a pay journal: totals per earning and deduction, net pay by bank and by cash, advances and loans given and recovered.
AE-R2 HR or accounts maps each pay component to a ledger name once.
AE-R3 The journal can be split by branch, department or payroll group.
AE-R4 Export as a spreadsheet and as a file that can be imported into Tally. The exact Tally format is to be confirmed.
AE-R5 An export is marked as sent, and a re-export after an adjustment shows only the difference.

AE-02 Journal split: none / branch / department / payroll group. Default branch.
AE-03 One journal per pay run / one per month. Default per pay run.
AE-04 Daily allowance cash payouts included as: a daily entry / a period total. Default period total.

======================================================================
12. FIXED BUSINESS RULES (NOT CONFIGURABLE)
======================================================================

BR-01 Raw punches are never edited or deleted. A correction is a new punch marked manual, with a reason and an approver.
BR-02 All calculation is rule-based and repeatable. No AI judgement in the calculation path.
BR-03 Any new or changed input for an open period recalculates the affected days and totals.
BR-04 No double penalty. One shortfall produces at most one pay effect; where two rules apply, the larger applies once.
BR-05 The most specific policy assignment wins, using the version in force on the date.
BR-06 A locked period and a closed pay run never change. A later correction posts only the difference to the next open period.
BR-07 Nobody approves their own request.
BR-08 Every pay-affecting result stores its explanation: punches, rule, version, approval.
BR-09 A missing check-out is a missed punch, never an early check-out.
BR-10 Count-based and minutes-based penalties are applied at period end, after regularisation is settled.
BR-11 Times are stored in UTC with the branch's time zone. Exact times are stored; rounding affects totals only.
BR-12 Net pay is never negative.
BR-13 The daily allowance is never part of the salary figure, and a deduction set to come from the allowance never reaches the salary.
BR-14 A disabled module or rule has no effect on any result.
BR-15 Money rounding. Rates (per-day, per-hour, per-minute, overtime) are never rounded inside a calculation. Each amount is rounded to 2 decimals (paise) once, when it becomes a line on the payslip or in a report, using round half up (0.005 rounds up). Totals are the sum of the rounded lines. Net pay is then rounded by PY-06. When net pay is split into bank and cash, the two portions always add up exactly to net pay; which portion takes the rounding difference, and whether cash is paid in whole rupees, is open (Q18).

Order of checks for a late arrival (early check-out follows the same order, mirrored):
1. Day covered by leave, on-duty, holiday, weekly off or an exemption: not late.
2. Expected start moved for half-day leave or an approved permission.
3. Within grace, with grace uses remaining: on time.
4. Approved regularisation or bulk waiver: waived.
5. Conversion to a permission, if enabled and balance is available.
6. Compensation by extra work, if enabled and satisfied: waived.
7. Slab action applied, and the minutes passed to the money deduction rule if PD-01 is on.
8. If the result is a late mark, it is counted for period-end penalties.

13. WORKED EXAMPLES

13.1 ATTENDANCE

Unless stated: fixed shift 09:00 to 18:00, 60-minute fixed break 13:00 to 14:00, 8 required hours, shift-based status, late grace 10 minutes, early grace 5 minutes, default slabs, permission limit 2 per month.

E1. Within grace
In 09:08. Result: on time, no mark.

E2. Late mark
In 09:25, out 18:00. 25 minutes late, slab 11 to 120. Result: present, one late mark.

E3. Late converted to permission (LA-15 = automatic)
In 09:25, 2 permissions left. A 30-minute permission (09:00 to 09:30) is used. Result: present, no late mark, 1 permission left.

E4. Late made up the same day (LA-13 on)
In 09:25, out 18:30. 25 late minutes are covered by 30 extra minutes. Result: present, no late mark. Net hours 8 h 05.

E5. Count-based penalty (LA-06 on, every 3rd late mark = half day)
4 late marks in the period. One penalty of half a day at the 3rd mark. Recovered from casual leave; if the balance is zero, 0.5 day loss of pay.

E6. Very late
In 11:30, out 18:00. 150 minutes late, slab above 120. Result: half day present, half day absent. Not counted as a late mark (LA-23 = no).

E7. Early check-out
In 09:00, out 17:20. 40 minutes early, slab 6 to 120. Result: present, one early mark.

E8. Hours-based status (flexible shift, 8 required hours)
In 10:15, out 18:30, 60-minute break. Net 7 h 15, shortfall 45 minutes, above the 15-minute tolerance. With DS-05 = half day: half day. With DS-05 = deduct actual minutes: full day less 45 minutes. No separate late or early penalty.

E9. Permission at end of shift
Approved permission 16:00 to 18:00. Out 16:02. Result: present, no early mark, permission time counts as worked, 1 permission left.

E10. Permission over-stay
Approved permission 10:00 to 11:00. Out 10:00, back in 11:25. The extra 25 minutes count as late minutes. Result: present, one late mark.

E11. Third permission in the month
Limit is 2. With PM-18 = block: the request is refused and the employee can apply for half-day leave. With PM-18 = allow with HR approval as unpaid minutes: 60 minutes are deducted once HR approves.

E12. Half-day leave plus late
First-half leave approved. SH-11 is set to a fixed time, so the second half starts 14:00. In 14:20, out 18:00. 20 minutes late against the adjusted start. Result: half day leave, half day present, one late mark.

E13. Missed check-out
In 09:00, no out. Reminder sent at 18:30 and next morning. Employee requests 18:05; manager approves. Result: present. If still unresolved at the cut-off, MP-03 applies.

E14. Bulk waiver
Heavy rain on one date. HR waives late arrival for one location. All late marks for that date and location are cleared, with the reason logged.

E15. Correction after lock
28 October was marked absent and October is locked. On 5 November the day is corrected to present. Result: October is unchanged; the November payroll input carries a one-day arrear tagged 28 October.

E16. On-duty for part of the day
Approved on-duty 14:00 to 18:00 at a client site. In 09:00, out 13:55, no further punch. Result: present, full day, no early mark; the on-duty hours count as worked.

E17. Punch at another branch
Master branch A, allowed branch B. In and out at B. Result: present under the employee's own shift and rules; the day is costed to branch B. A punch at branch C, which is not allowed, is recorded and flagged for approval.

E18. Web check-in with location and geo-fence
Branch fence radius 200 metres, PC-04 = record and flag. Web check-in 60 metres from the centre: accepted. Web check-in 450 metres away: recorded and flagged, and not counted until the manager approves. Location permission refused in the browser: the punch is blocked (PC-13) and the employee is told why.

E19. Absconding (LM-29 on, 7 days)
7 continuous uninformed absent days. Result: employee flagged as absconding, HR alerted, pay held until HR returns the employee to active or starts offboarding.

13.2 PAY

Unless stated: monthly salary 15,000 rupees, day divisor 26, 8-hour shift. Per-day rate = 15,000 / 26 = 576.923... (shown as 576.92). Per-minute rate = 15,000 / 26 / 8 / 60 = 1.20192... (shown as 1.2019). Rates are not rounded in calculation; each amount is rounded to 2 decimals as a line (BR-15).

P1. Daily allowance on top of salary
Allowance 50 per day, 26 days worked in the month. Allowance earned = 1,300, paid in cash day by day. Salary = 15,000. Total received = 16,300. CTC shows 15,000.

P2. Late deduction, fixed method, from salary
20 rupees per 15 minutes, part block counts as full. 25 minutes late = 2 blocks = 40 deducted from salary.

P3. Late deduction, per-minute method, from salary
25 minutes late x 1.20192... = 30.048, rounded to 30.05, deducted from salary.

P4. Late deduction from the daily allowance
Same fixed method, allowance 50. 25 minutes late = 40. Allowance paid for the day = 10. Salary untouched.

P5. Deduction larger than the allowance
50 minutes late = 4 blocks = 80. Allowance for the day becomes 0. The remaining 30 is not taken from salary and is not carried forward.

P6. Uninformed absence
One absent day with no approved leave. Cut = 2 days = 1,153.85. If a leave request for that day is approved later, the extra day is reversed.

P7. Excess absence, informed and uninformed kept separate
Informed part: X = 3, Y = 1 for each day beyond X. Uninformed part: X = 2, Y = 1 for each day beyond X. Uninformed absence rule (LM-21) off. In the month: 5 approved paid leave days and 3 uninformed absent days.
Informed: 2 days beyond X = 2 days cut. Uninformed: 3 days loss of pay, plus 1 day beyond X = 1 more day cut.
Total cut = 2 + 3 + 1 = 6 days, shown as separate lines: excess informed leave 2 days = 1,153.85; loss of pay 3 days = 1,730.77; excess uninformed absence 1 day = 576.92. Total = 3,461.54.

P8. Comp-off not taken
Worked on a Sunday, comp-off approved, expiry 60 days. Not taken by expiry: one extra day's wage of 576.92 is paid in that period.

P9. Advance
Advance of 3,000 given on the 10th. Net pay before recovery is 14,000. Recovered in full; net paid 11,000.

P10. Loan
Loan of 12,000 over 6 instalments = 2,000 per month for 6 months, no interest.

P11. Recovery larger than the cap
Weekly-paid worker, net pay for the week 2,400, recovery due 2,000, cap 50%. Recovered 1,200; 800 carries to the next pay.

P12. Bank and cash split
Net pay 14,500. Fixed bank amount 10,000: bank 10,000, cash 4,500. Or 60% bank: bank 8,700, cash 5,800. One payslip shows both. With a percentage split, bank and cash always add up to net pay; how a paise difference is assigned is open (Q18).

P13. Night-shift allowance
100 per night, 10 night shifts in the month = 1,000, shown separately from salary.

P14. Daily wage
Rate 600 per day, weekly pay, 5.5 payable days in the week = 3,300.

P15. Extra shift
Daily wage 600. Works a second rostered shift the same day, approved. Paid 1,200 for the day, with no overtime on top.

P16. Earned weekly off
Needs 6 days present in the week. Present 4 days: the weekly off is unpaid, one deduction day = 576.92, in addition to loss of pay for the 2 absent days.

P17. Rounding tie
Hourly wage 150.15, 7.5 payable hours. 150.15 x 7.5 = 1,126.125, rounded half up to 1,126.13 (BR-15).

18. RISKS AND COMPLIANCE
======================================================================

K1. Double cuts for absence, deductions for approved leave beyond a threshold, money deductions for lateness, overtime rates and deductions from allowances are governed by labour law that varies by state and type of establishment. Each rule must be reviewed by a labour-law consultant before it is switched on for a client.
K2. Payment and statutory records must show whatever each organisation is legally required to record, including for cash payments. The payslip and registers should be reviewed for this before go-live.
K3. Too many settings can overwhelm HR. Mitigation: sector templates, plain-language summaries, test run.
K4. Settings can conflict (for example a day-count penalty and a money deduction for the same lateness). Mitigation: fixed order of checks, BR-04, warnings when saving.
K5. Identity documents, bank details, location and face images are sensitive personal data. Consent, purpose, access and retention need a privacy review.
K6. Daily cash payouts are made before all corrections are known. Mitigation: next-morning calculation and adjustment in the next payout.
K7. Module combinations multiply test cases. Mitigation: each module reads only defined inputs from the common part (MD-06).
K8. Client-specific rules can grow into many one-off variations that are costly to maintain and test. Mitigation: defined points where rules plug in, a test run against the last closed period, and promotion of repeated rules into the standard base (CR-R4, CR-R6).
K9. Browser location on desktop computers without GPS can be inaccurate by hundreds of metres, which can wrongly place a web punch outside the fence. Mitigation: the accuracy setting (PC-14), flag-not-block as the default (PC-04), and the IP restriction as an alternative check (PC-15).

TB-01 Separate organisation handling. Every record carries its organisation. The database itself, not only the application, refuses to return or change a record that belongs to another organisation. TB-03 Timed work. Daily processing, reminders, escalations, period-end penalties, leave accrual, comp-off expiry and device-offline alerts are started by Google Cloud Scheduler. A failed run is retried and shown in the vendor health view (VC-R8). Every timed job is safe to run twice.
TB-04 Device connection. Punch devices must reach the server over a secure connection. Where a device model cannot, punches pass through an approved relay. To be confirmed for the eSSL models in use.
TB-05 Money. All amounts are stored and calculated as exact decimals. Rounding happens only as BR-15 states (each amount line to 2 decimals, half up) and where a setting says so (PY-06 net pay).
TB-06 Portability. The database uses standard Postgres features only, so it can move off Supabase without redesign. Sign-in and file storage do not depend on Supabase.
TB-07 Data location. All data and files are held in the India region.
TB-08 Backups. Daily backups from the start; point-in-time recovery once live payroll data is held.
TB-09 Environments. Test and live are separate. Client data is not copied into test without masking.
